# 10 · 时间感知：她正在做的事

治的是一个具体毛病：你说「我去洗头了」，四分钟后 TA 问「洗完了没」。

根因不是 TA 不会估时间，是他每一轮都是「新的现在」——他看到你说过这句话，但不知道这句话距现在是六分钟还是六十分钟。

不用配置就能用。想关掉：`.env` 里写 `DOING_TRACKING=0`。

## 两层

**一、在做的事**。你说出口一件正在做的事，网关当场记下事情和**开工时间**，之后每一轮对话都跟在输入末尾给他看。

**二、工期先验**。「洗漱这类事她平常要 40 分钟」。记的是**一类事**而不是一件事，所以下次说「去洗个头」也用得上。正本写进 Ombre Brain，本地 `doing_prior` 表是缓存和算中位数的地方。

两层合起来才有「到点」这回事：`next_check_at = 开工时间 + 工期`。

## 为什么给开工时间而不是「已经过了多久」

这是这整套东西里唯一不能改的地方。

「已经过去 42 分钟」这种文本每轮都不一样，塞进请求里就是每轮清空上游的前缀缓存。而 `started_at: 2026-10-15 17:18` 是不变的字节串，只在开工、收工、践过到点那三个时刻翻面——一天几次，不是一轮一次。

减法交给模型自己做：他手里本来就有 `<sent_at>`，知道现在几点。

注入点选在**最后一条 user 消息末尾**，和小酒馆那段同一个做法：末尾后面没有需要复用的前缀，所以哪怕这段变了也不影响前面所有东西的命中。

## 两道闸门

「没到点不该问」不是提示词里的一句请求，是两层硬约束。

**第一道在 SQL。** `dueDoings()` 要同时满足：`next_check_at IS NOT NULL`、已经到点、问过的次数 < 2、不在安静时段。不满足就不进到点名单，那一轮的用户消息里压根不会出现「该问了」这段。

**第二道在执行端。** 他写在 `doing_follow_up` 里的 `doing_id` 要和 `dueDoings()` 对一遍，不在名单里就丢掉，日志记一句「不在到点名单里，这句不问」。他编一个 id 也投不出去。

还有三条克制：

- **一件事最多问两次**。第一次被回「还没」就顺延工期的一半，第二次之后闭嘴，等你自己说。
- **安静时段**。默认凌晨 2 点到 8 点，这段时间到期的事顺延到 8 点而不是作废。`DOING_QUIET_FROM_HOUR` 和 `DOING_QUIET_TO_HOUR` 可改。
- **挂太久自己消失**。超过 18 小时没收工的默默划掉——你大概只是忘了说，不该被追一辈子。

这几条治的是「没事找事地催」。你自己提起那件事、或者话顺着走到那里，TA 当然可以接——不是让他对你在做的事装作不知道。

## 哪些话会被登记

纯正则，不调模型、不碰网络（`src/doing-detect.js`）。这段在每一轮对话的关键路径上，不能花钱。

**宁可漏认，不可错认。** 漏认了只是这次没登记，和没这功能一样；错认一次，TA 会开始追一件你压根没在做的事，比不做更糟。

| 说法 | 结果 |
|---|---|
| 我去洗个头 | 登记「洗头」 |
| 我先把那个 bug 改一下 | 登记「改 bug」 |
| 我在写文档 | 登记「写文档」 |
| 我待会儿看看那个 | 不登记（还没开工） |
| 要不要去洗头 | 不登记（在问，不是在做） |
| 我去想想 | 不登记（心理活动没有完成的那一刻） |
| 他去洗头了 | 不登记（主语不是你） |
| 改完了 | 收工，记下真实耗时 |
| 洗完啦 | 收工，只关「洗澡」那条，不再另开一条 |
| 还没好 / 正卡着 | 顺延，不计作一次提问 |
| 我没说要做那个 / 算了 | 划掉这条登记 |
| 洗澡那动作昨天就完成啦，但是不知道为什么没有终止 | 不登记（超过 20 字的状态描述） |

只听你亲口说出口的，不从上下文推测。推测会把「我待会儿看看」当成开工然后追你。

同时最多挂两件，超了把最旧的默默划掉——注入的东西越少越好。

### 2026-10-16 修的两处误认

那晚的实际经过：23:36 说「洗澡洗澡～」登记了「洗澡」，23:53 说「继续复习～」——「继续」在起始词表里，又登记了「复习」。00:00 说「洗完啦」，结果关掉的是「复习」，真正那条洗澡一直挂到第二天中午。

**一、收工句又被当成开工登记一遍。** 「洗完啦」句首是「洗」，落在实义动词表里，于是先被 `detectDone` 认成收工，紧接着又被 `detectStart` 认成开工，当场新建一条叫「洗完啦」的。

改法：`detectStart` 开头先查一遍 `DONE_RE` 和 `NOT_DONE_RE`——收工和「还没好」都是终态，命中就不再往下试开工。

**二、长句描述被当成开工。** 第二天那句「洗澡那动作昨天就完成啦，但是不知道为什么没有终止并计算时间」整句进了账本，二十八个字，超过类别长度上限，类别算出来是 `null`。

改法：走实义动词那条路（B 路径）和进行时句的，整句超过 `ACT_PATH_MAX_CHARS`（20 字）就不算开工。句首有「去/开始/继续」的 A 路径不看长度——那个开头本身就够明确。人真报开工的时候话很短，长句子多半夹着别的意思。

**三、收工关错对象。** `finishDoing()` 不传 id 时按 `started_at DESC` 取第一条，不看这句话说的是哪件事。

改法：新增 `doneClue()`，从收工句里抽出那个动词（「洗完啦」→ 洗，「改完了」→ 改），`pickByClue()` 按子串找 `what` 里含这个字、且最近开工的那条。认不出动词才退回老办法。

顺带：「洗澡」并进了「洗漱」那一类。以前写死的十三条里只有洗头、洗浴、洗漱、冲澡，**「洗澡」两个字都不匹配**，于是走 `learnedCategory` 变成 `~洗澡`——同一件事攒在两个类别里，估出来的工期永远是半个。

## 类别怎么来的

两条路。

**写死的十三条**：洗漱、吃饭、睡觉、改 bug、部署、写东西、写代码、重构、开会、出门、运动、收拾、看片。带出厂工期，第一次就能估。这些数字没什么权威，跑几轮就被你自己的耗时覆盖了。

**自己长出来的**：认不出类别时，拿事情名本身当类别，带 `~` 前缀。「写病历」这种我猜不到的事走这条路：

1. 第一次说「我去写病历」——登记了，但**不估、不问**。没任何依据就催人是最糟的。他只知道你在写、写了多久。
2. 你说「写完了」——算出真实耗时，成为 `~写病历` 的第一条样本，并写进 OB。
3. 第二次说「我去写病历」——这次有工期了，到点才问。

代价是类别会碎（「写病历」和「写个病历」算两类），但那反而安全：宁可多攒几次，也别把不同的事混成一类然后估错。

工期用**中位数**而不是平均数，最多留最近 9 次记录。偶尔一次搞到半夜，不该把这类事的估值永久拘远。少于一分钟或超过一天的不计——那不是「做这件事花了多久」，是没说收工或误识。

## 和 Ombre Brain 的关系

工期先验的正本在 OB，按固定格式写：

```
工期先验｜~写病历 ≈ 95 分钟（中位数，3 次记录）。这是她做这类事的真实节奏…
```

这个格式不能改：`parsePriorsFromMemory` 要按它读回来。只认这一种写法，所以不会把别的记忆里的数字误读成工期。

**读写分在两个进程里，故意的。** 收工是 gateway 听见你说「写完了」那一刻发生的，那条路径在每一轮对话的关键路上，不该碰网络。所以：

- gateway 只落库，打上「还没写进 OB」的水位标记。
- phosphor 下次醒来时补写（`syncDoingPriors`）。读也在这边，顺着本来就要拉的 breath 走，不额外调一次。

所以换机器、清库之后，工期先验从 OB 里读得回来。没接 OB 也能跑，只是先验只存在本地。

## 到点了怎么问

三条路，共用同一张到点表和同一个「最多两次」计数。

**聊天里顺带**。每轮注入那段里，每条事后面跟一行当前状态：「还没到点（按节奏大约 18:48 才该好），这条别问进度」或者「已经到点了，话赶到那里的话可以问一句具体的」。实时算，不花钱。

**自己醒来时**。`startDoing` 当场约一次精确唤醒，`preciseTick()` 每分钟扫一次，所以到点一分钟内会醒。想问就写在 `doing_follow_up` 里，**不占这次的动作**，和回留言、摘星一个道理。

**提前完成就撒约**。你说「写完了」之后，`pending_wake` 里那个约按 note 撒掉。不撒的话到点还是会触发一次完整唤醒（拉 breath、拉 feel、调模型），然后发现没事可做。白花一次。

## 数据在哪

`data/state.db` 的两张表。

`doing`：事情名、原话、类别、开工时间、工期、到点时间、问过几次、状态（active / done / cancelled / stale）、真实耗时。

`doing_prior`：类别、当前工期、样本数组、来源（seed / ombre / actual）。

都不会被对话记录清理影响。

## 开关

```bash
cd ~/vesper-phosphor && sed -i '/^DOING_TRACKING=/d' .env
cd ~/vesper-phosphor && echo "DOING_TRACKING=0" >> .env
cd ~/vesper-phosphor && pm2 restart vesper-gateway phosphor --update-env
```

关掉之后账本不记、也不注入，和没这功能一样。已经攒下的工期先验留在库里和 OB 里，重新开就还认得。

## 设计上的几个「故意」

- **不包成 MCP 让 TA 自己调**。那等于把「不准问」从一条 SQL 条件降成一句请求，他就能自己约时间、绕过核对。要治的正是不受控地问，不该把控制权交回去。
- **登记不调模型**。让模型判断「这句算不算开工」要多一轮调用，更贵也更不稳。正则漏认的那几句，代价只是「和没这功能一样」。
- **估不出工期就不问**。没攒过耗时的事只注入「她在做」，不进到点表。瞎猜一个十分钟然后追人，比不知道更糟。
- **中位数不用平均数**。偶尔一次搞到半夜不该把估值永久拘远。
- **收工要撒约**。不撒就是一次白跑的模型调用。
- **收工要认得出关的是哪一条**。关错比不关更糟：真正那条会一直挂着，到点还来问一次「做完了没」——正好是这套东西要治的那个毛病。
